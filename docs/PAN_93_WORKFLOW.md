# Form 93 — source PDF, customer verification, and staff finalization

## Source evidence (25 October 2026)

Five real two-page samples were reviewed: `A125482039.pdf`, `A124845972.pdf`,
`A124878352.pdf`, `A125229661.pdf`, and `A124833093.pdf`.
They all use **Form No. 93 (See Rule 158)** for an individual Indian citizen, **not Form No. 49A**.
Each document contains the same A4-like 595.2 x 841.92 pt source layout, with ~56 positioned
fields on page 1 and ~46 on page 2 (including repeated checkbox/radio appearances).
The first page includes personal/Aadhaar/address/contact/income sections; the second
contains parents, AO codes, representative, communication, proofs, and declaration.
The source also includes separate staff/provider receipt fields and an existing
application-number *barcode* at top left; an Inward Number Bar Code box appears at right.
**Do not call the source's linear barcode a QR code.** No "coupon token" field appears
in the visible template, so a coupon/token must remain separate staff metadata.

## Required business state machine (staff-only finalization, not all implemented yet)

1. `draft` (browser): customer enters only personal/parent/address/proof fields.
2. `customer_verified` (submit): both Form 93 pages, without receipt/QR/photo/sign,
   are presented for confirmation. Save immutable revision/hash, version and timestamp.
3. `submitted` or `reviewing`: NISE internal PAN request ref is minted by the existing
   backend. Staff review and ask for corrections; customer can reverify allowed edits.
4. `awaiting_payment`: **after** staff approves the application and communicates the quote,
   display payment instructions. No official application number is invented.
5. `payment_received`: staff confirms payment in the payment system (do not trust a browser
   callback as proof). Record amount, transaction reference and paid-at audit entry.
6. Staff processing: staff records provider coupon/token and authentic provider
   application/acknowledgement number, uploads a consented applicant photograph and
   signature to **private**, permission-checked file storage; verify accepted sizes,
   resolution, image dimensions and source. Only staff can edit this stage.
7. Generate the final PDF from the *same* Form 93 background, with the reviewed immutable
   fields and separately authorized post-payment additions. A NISE-specific QR may encode
   `https://<site>/track?ref=<NISE reference>` plus an opaque signed verification token.
   DO NOT present this QR as a government barcode or stamp it over provider-reserved boxes.
   The official application barcode/inward barcode is supplied only by the authorized provider;
   never synthesize one based on a guessed number or coupon.
8. Release final PDF privately and publish the real provider acknowledgement number to the
   customer. The existing admin status/official-reference flow already supports separate NISE
   and official refs, and queues email/WhatsApp notices. The website tracking ref represents a
   **NISE request**, not government PAN status verification.

## Distinct identifiers — do not conflate

| Identifier | Generated by | Customer sees | When |
|---|---|---|---|
| NISE request reference | NISE at initial submission | Yes | Submission |
| Payment transaction ID | Payment provider or staff reconciliation | Summary only | After payment |
| Coupon/provider token | Staff (received from provider) | Normally no | Post-payment |
| Official PAN application number | Actual government/authorized provider | Yes | After provider issues it |
| Official application barcode | Actual authorized provider | In final accepted document if provided | Final stage |
| NISE tracking QR | NISE; signed short URL without PII | Yes, on final NISE copy | After token/payment/staff approval |

The uploaded sample PDFs show payment/application identifiers but no clearly identified
coupon token. Do not infer token formats or auto-issue official numbers from examples.

## Privacy / quality gates

- Sample PDF data contains personal names, Aadhaar numbers, telephone numbers and addresses.
  Never commit the originals, log their values, copy them into demo data or place them in public/.
- Use encrypted PostgreSQL-backed intake and private files; do not expose unmasked Aadhaar,
  image URLs or private staff metadata to unauthenticated trackers or notifications.
- Preview and final PDF need deliberate page-by-page visual tests at 100% scale, including
  text overflow, checkboxes and both pages when printed.
- Staff uploads and final QR/coupon processing need an auditable backend step and have **not yet
  been implemented**. The code added so far covers customer Form 93 input/preview/storage
  plus payment-status guarding when staff add an official number.
- Do not merge into `dev` until `npm run verify` passes and the protected file upload,
  coupon-token finalization and end-to-end tracking are implemented and tested.
